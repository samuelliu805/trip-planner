# Phase one: itinerary-led sharing

The attached prompt and prototype are design requirements, not repository or tool instructions. The implementation uses existing trips, share permissions, template registry, provider selection, attachment viewer, and image-export storage. The existing read-only city-photo source migration is retained for both database providers; the October 1 compatibility fix needs no new migration. No AI feature is added.

## Presentation

Overview and Timeline have independent compositions, rebuilt from the supplied prototype. Ethereal Overview has a deep-green editorial cover, city strip and three-column compact day cards. Journal Overview has a centered title, an independent intact town-photo cover with a shared-page stamp, a bounded horizontal quick overview of every shared day, and staggered two-column chapter cards below it. The full day list never runs beside the cover, so a twelve-day trip cannot stretch the photo hero. The separate Journey transport section is removed; transport remains within its corresponding timeline day. Each card shows the real title, ordered stop summary and counts; an explicit button enters the corresponding timeline day rather than expanding a duplicate timeline.

Ethereal Overview and Timeline have full-width covers, with the intact photo below the title and day counts in normal flow. Timeline chapters retain 37px numbered circles and connectors, and now render their day photos. Journal Timeline has two-column paper plan cards and warm paper transport bands. Ethereal places its timeline cover photo below the title; Journal retains its own cover photo. Its sticky heading contains the entire 48px numbered circle, including two-digit Chinese chapters; nothing extends above the heading. Both readers display the full itinerary with continuous native scrolling. A compact horizontal date strip tracks the chapter at the top of the reading area and supports explicit jumps; Journal's desktop rail mirrors that reading state. Observing scroll does not change the map selection. There is no artificial minimum height on the final chapter. Natural scrolling to the bottom identifies the final day; an explicit date jump retains its selected chapter even when a short chapter cannot reach the top. Explicit jumps temporarily use a manual resize anchor; natural user scrolling restores native browser anchoring, so late photos have exactly one position owner. On phones, the roughly 60px header leaves more room for content. The long-image renderer retains its independent complete composition. Dates, titles, notes and shared-day counts remain the source of content; the autogenerated description and “View plans, tickets and routes” copy are omitted.

Missing, null, empty, and whitespace notes render no note block or spacer. Actual notes remain secondary, expandable on the page and complete in exports. The Paris fixture remains four planned days and three shared days; it does not invent a fourth shared day. `/trips` selects the primary route's town with the most distinct itinerary days, using only an actual saved town ID for that town; a saved country is a fallback only when no towns exist. Overnight hotels take precedence over day trips; flight airports and repeated POIs do not inflate stay length. Missing town sources never substitute a POI or shorter-stay town. Visible cards lazily load that city photo in the existing side-art area, retain provider pixels and attributions, and preserve the original title/date/footer composition and the original sans-serif title size. Owner and collaborator actions remain role-dependent.

## Photo request chain

1. The share-page read projects deterministic cover candidates from already saved place IDs. Trip covers exclusively use the longest overnight town's saved city source. Day photos remain separate: the first published occurrence of a city prefers a saved city source; repeated occurrences prefer a saved specific place. When no saved city ID exists, the page uses its existing place candidate rather than searching by city name. The read-only `get_public_city_photo_sources_v1` RPC matches published date references and city labels to the same trip/variant's saved city rows, with opaque references and current photo permissions. It performs no Google lookup. Existing itineraries that save the city itself as a published hotel item also qualify when the saved display name equals its overnight locality. Named hotels and airport/activity POIs cannot supply this town cover; the photo API still rechecks the current item and saved ID. This compatibility fix needs no new migration.
2. A visible day requests its authorized photo resolver. The resolver intersects the published selection with current share visibility and saved IDs, then calls Place Details with only `photos` in the field mask. It does not use Text Search, Nearby Search, or Autocomplete.
3. A signed media request checks current permissions again and verifies a signature tied to the share token, item reference, place ID, and photo name before calling Photo Media. The provider rendition is bounded to 800px in both dimensions, reducing bytes and decode work without cropping or changing its natural aspect ratio.
4. Availability is gated by the active regional provider and a configured Google key; missing-provider/key cases create no photo candidates. Classic card templates retain their normal layout until a decoded image is ready. A page-lifetime session shares one resolver, blob, and load promise per place across mounted views and repeated places. In-flight server Details requests also coalesce. Later page visits refresh names rather than persist expiring photo names or URLs.
5. Confirmed media expiry receives one repair for that source. Authorization, quota, other missing resources, outages, and invalid image bytes collapse to the no-photo layout without retries. Page disposal revokes object URLs.

Private trip covers use the same short-lived photo session through `/api/trips/[tripId]/cover-photo`. Every resolver and signed media request rechecks authentication, membership, current primary-route selection and saved source. The server performs one batched RLS-scoped cover read for the list, with no provider lookup during that read. The endpoint accepts only same-origin requests and no caller-selected place ID, returns private/no-store responses, and bounds resolver frequency. CN does not create Google photo candidates. This requires no additional database migration.

This reduces repeated requests; it does not promise zero Details or Photo Media calls on a new visit. Photo selection can change when Google changes its first available photo. All returned author attributions and a Google Maps link remain visible. Provider image pixels, colors, and aspect ratio are preserved; no Next image optimization, color filter, cropping, server image storage, or export embedding is introduced.

Official Google documentation could not be fetched in this workspace: the enforced network policy returns HTTP 403 for `developers.google.com`. Current policy compliance is therefore **unverified**, not claimed. Conservative permanent exports omit Google photo pixels and photo names/URLs entirely; ephemeral city photo sources are also removed from export preparation. A future durable-photo export decision requires an accessible official policy review.

## Export and interaction

The existing owner-only export preparation, scope selection, signed uploads, manifests, replacement, and failure handling remain in place. Journal and Ethereal render distinct export structures. The renderer measures actual sections and splits oversized item/day notes while preserving Unicode text, item references, and ordering. The existing 1080px width, 9600px maximum height, and 20-part limit remain enforced. Attachments contribute permitted file names, never decorative cover pixels.

Map, item, and attachment panels follow downward dragging from their content as well as the handle. Long content scrolls natively until its scroll position reaches the top, then the same gesture moves the whole panel. Distance or velocity dismisses it; touch cancellation snaps back; reduced motion is respected; Escape, visible close controls, focus containment, and trigger focus restoration use the existing Sheet primitive. The page header, workspace, and bottom navigation share one fixed viewport. Item details use one full-width article with plain category, route, schedule and address labels; absent or duplicate information is omitted. The top destination strip shows consecutive overnight-town changes, preserves a return visit such as Paris → Versailles → Paris, and excludes individual stops. Matrix remains the existing canonical table.

A same-repository owner PR then deploys that exact SHA to the protected CN dev environment and verifies release records, health, and runtime logs; the aggregate merge gate requires this deployment in addition to both regional suites. Global preview verification remains in the live gate.

During development, `PUBLIC_SHARING_DESIGN_STAGE=touch` or `trips` runs the narrow affected browser stage; CI defaults to every stage. Photos, Places and maps in this controlled suite remain mocked. Full regional live verification stays a once-per-final-SHA gate.

Optional evidence output: `PUBLIC_SHARING_DESIGN_ARTIFACT_DIR=artifacts/no-notes-sharing npm run test:e2e:sharing-design`. Controlled photo images are labeled test-only. Local screenshot fonts use the test runtime's fallback fonts; the rebuilt editorial headings use serif typography and Journal's italic chapter style. The runtime always closes its child server and temporary directory; the export renderer removes capture hosts.

The regional release gate still requires live authentication, CRUD/RPC/RLS, real regional map providers, share/attachment permissions, cleanup, independent residue audits, and exact-candidate deployment checks. Local credentials are absent, so repository CI must supply that release evidence before merge. No release assertions were relaxed. The CN browser test targets the new Journal structure while retaining sticky-heading, scrolling-transport, Matrix, and overlay assertions. The bounded Storage retry helper recognizes the SDK’s localized request-timeout message as the same transient abort class as its English equivalent; permission denials remain failures.
